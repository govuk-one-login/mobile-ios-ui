# New SharedScreens package: QR ScanningViewController + DialogView extracted from the app

This branch stands up a new `SharedScreens` Swift Package target and moves the QR scanner screen and the loading/success `DialogView` into it, so both can be shared across apps instead of living in a single product. The scanner is rebuilt around injectable `CaptureSession` / `CaptureDevice` / orientation protocols so it can be unit-tested without a live camera, and a 17-test suite drives construction, the capture lifecycle, cleanup, error routing, and barcode parsing through mocks. The bulk of the churn after the initial copy is Swift 6 concurrency hardening: `detectedBarcode` and `captureOutput` are made `nonisolated`, a fresh Vision request is built per frame to avoid running a main-actor-constructed closure on a background queue, and `isScanning` is serialized behind a dedicated queue. Duplicated extensions, fonts, and localisation were repointed at `DesignSystem` where possible.

Watch for: the committed `SharedScreensTests.xcscheme` does not run as configured — it hosts the tests in `DesignSystemDemo.app` and resolves to a "My Mac" destination, failing with "no test bundles available"; tests only run through the SwiftPM-generated scheme (confirmed). `swift build`/`swift test` on macOS also fail because the iOS-only `DialogView.xib` cannot compile for mac, so CI must target an iOS destination (confirmed). The capture-setup error path swallows the underlying `AVFoundation` error and reports `nil` (confirmed). Several copied `Localizable.strings` entries are dead and the `en`/`cy` tables are asymmetric (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The scanner's testability rests on three injected protocols (`CaptureSession`, `CaptureDevice`, orientation) with `AVFoundation` types retrofitted to conform. This is the central design choice and it works — the suite exercises the real control flow against mocks, and all 17 tests pass on an iOS simulator under `-swift-version 6`.

The Swift 6 concurrency story is the riskiest surface and it has been thought through. `detectedBarcode` and `captureOutput` run `nonisolated` on the background `processingQueue`, a fresh `VNImageBasedRequest` is constructed per frame so the completion closure carries no main-actor isolation, `isScanning` is guarded by a serial queue, and the `nonisolated deinit` uses `MainActor.assumeIsolated` to run main-actor cleanup. The reasoning is documented inline and the code compiles without concurrency warnings.

Session start and stop are asymmetric: `startRunning` is dispatched to a background queue but `stopRunning` runs synchronously on the main thread, which blocks the main thread on a call `AVFoundation` documents as blocking.

The capture-setup failure path routes device-unavailable, input-construction, and output-rejection cases through a single `errorHandler(nil)`, discarding the thrown `AVFoundation` error — so a consumer handling camera-permission denial gets a `nil` cause.

The extraction from `DesignSystem` is mostly clean (fonts, `GDSLocalisedString`, `setBackButtonTitle`, `bindToSuperviewEdges`, `VoiceOverFocus` are all consumed from `DesignSystem`), but the bundled `Localizable.strings` were copied wholesale: only `GDSCommonBackButton` is actually referenced, the rest are dead, and `cy.lproj` carries numbered-list/number keys that `en.lproj` lacks.

Package wiring is correct — the `SharedScreens` target, its `DesignSystem` dependency, resource processing, and the `SharedScreensTests` test target are all declared — but the Xcode scheme committed to drive those tests is wired to the wrong host and does not run.

### Transport-agnostic scanner via injected protocols

The scanner no longer reaches for `AVCaptureSession`/`AVCaptureDevice` directly. `ScanningViewController` is generic over `CaptureSession` and takes a `CaptureDevice.Type`, a `VNImageBasedRequest.Type`, and an `errorHandler` through its initialiser, all defaulting to the real `AVFoundation` types. `AVCaptureSession` and `AVCaptureDevice` are retrofitted onto the new protocols via extensions. This is what makes the screen unit-testable: `MockCaptureSession` records the output and toggles `isRunning`, `MockCaptureDevice`/`UnavailableCaptureDevice` drive the happy and failure paths, and `MockDetectBarcodeRequest`/`MockBarcodeRequest`/`MockBarcodeObservation` let the tests feed Vision results without a camera.

```
ScanningViewController<CaptureSession>
        │  init(captureDevice:captureSession:requestType:errorHandler:)
        ▼
  CaptureSession ◄── AVCaptureSession (prod)   ◄── MockCaptureSession (test)
  CaptureDevice  ◄── AVCaptureDevice  (prod)   ◄── Mock/Unavailable (test)
  requestType    ◄── VNDetectBarcodesRequest   ◄── MockDetectBarcodeRequest
```

The suite drives the real `viewWillAppear → makeScannerCaptureView` path via `beginAppearanceTransition`, so the capture wiring, overlay layout, and cleanup all execute against the mocks rather than being stubbed out.

### Swift 6 isolation of the Vision callback path

`captureOutput` is `nonisolated` and runs on `processingQueue`. Rather than reuse a single main-actor-constructed `VNImageBasedRequest`, it builds a fresh request per frame inside that nonisolated context:

```swift
let request = requestType.init { [weak self] request, error in
    self?.detectedBarcode(request, error)
}
```

Because the completion closure is created in a nonisolated context it carries no main-actor isolation, so Vision invoking it synchronously on the background queue is legal — this is what the "avoid EXC_BREAKPOINT" and "nonisolated to stop crash in Vision perform callback" commits are fixing. `detectedBarcode` is correspondingly `nonisolated`, touches only the thread-agnostic Vision `request`, and hops to the main actor via `Task { await self?.didScan(...) }`. `errorHandler` is `@Sendable` so it can be called from the background queue.

`isScanning` is the shared mutable state between the background capture callback and the main-actor `didScan`, and it is serialized behind `isScanningQueue` with a `nonisolated(unsafe)` backing var — a deliberate, contained escape hatch rather than an unaudited one. The `nonisolated deinit` runs main-actor `cleanup()` through `MainActor.assumeIsolated`, justified in a comment by UIKit always deallocating view controllers on the main thread.

One bounded gap in this path: multiple in-flight frames can each schedule a `didScan` `Task` before the first flips `isScanning` to `false`, since the flip happens on the main actor inside `didScan` rather than at enqueue time. The `guard isScanning else { return }` at the top of `didScan` absorbs the duplicates, so the effect is redundant `Task` scheduling, not a double scan.

### Session start/stop threading asymmetry

`startScanning` correctly moves the blocking `startRunning()` off the main thread:

```swift
DispatchQueue.global(qos: .userInitiated).async { session.startRunning() }
```

but `stopScanning` calls `captureSession.stopRunning()` synchronously, and `viewWillDisappear` and `cleanup()` both call it on the main thread. `AVCaptureSession.stopRunning()` is documented as a blocking call, so this blocks the main thread during teardown and on every disappear. The start path already shows the intended pattern; the stop path should match it.

### Capture-setup errors collapse to a nil cause

Every failure in `ScanningViewController+CaptureSetup` reports the same thing:

```swift
guard let videoCaptureDevice = captureDevice.for(mediaType: .video),
      let videoInput = try? videoCaptureDevice.input as? CaptureSession.Input else {
    errorHandler(nil)
    return
}
```

The `try?` discards the error thrown by `AVCaptureDeviceInput(device:)`, and the output-rejection branch also reports `nil`. A consumer wiring `errorHandler` to show a camera-permission or hardware-failure message receives `nil` and cannot distinguish "no camera", "permission denied", or "couldn't add output". `errorHandlerIsCalledWhenCaptureDeviceUnavailable` asserts exactly this lossy behaviour (`recorder.lastError == nil`), so the test encodes the gap rather than catching it. Propagating the caught error (and a typed error for the guard-only cases) would make the handler actionable.

### DesignSystem extraction: code shared, strings copied

The de-duplication is mostly thorough. `BaseViewController` and `DialogView` pull `GDSLocalisedString`, `DesignSystem.Font.Base.bodyBold`, `setBackButtonTitle`, `bindToSuperviewEdges`/`bindToSuperviewSafeArea`, and `VoiceOverFocus` from `DesignSystem` rather than re-copying them, and `setBackButtonTitle` was promoted to `public` in `Sources/Patterns/BaseScreen.swift` specifically to allow that cross-module use. `UIColor+Extensions` was trimmed to just the two colours the copied screens need, with a comment explaining the trim. The app-side `BaseViewModel` was renamed to `SharedScreensBaseViewModel` to avoid a clash.

The localisation did not get the same treatment. `BaseViewController` looks up `GDSCommonBackButton` in `.module`, so the target does need its own bundled strings — but only that one key is referenced anywhere in `SharedScreens`. The copied tables also carry `GDSCommonVoiceOverErrorPrefix`, `NumberedList`, the numbers `1`–`9`, `CardComponent`, and `GDSCommonCellAccessibilityHint`, none of which the extracted screens use, and `cy.lproj` includes the numbered-list and number keys while `en.lproj` omits them. Trimming to the used key and resyncing the two tables would remove the dead weight and the asymmetry.

### Cleanup lifecycle and the unused mock removal path

`cleanup()` is idempotent (guarded by `didCleanup`), stops scanning and animation, nils the sample-buffer delegate on `processingQueue` to avoid racing in-flight `captureOutput` calls, drops `videoDataOutput`, removes the preview layer, and breaks the layer→session reference. `deallocatesAfterCleanup`, `cleanupNilsSampleBufferDelegate`, and `cleanupRemovesPreviewLayer` cover this. What `cleanup()` does *not* do is remove the output from the session — and `MockCaptureSession` ships a `removeOutput`/`removedOutput` pair that nothing calls, because `CaptureSession` doesn't declare `removeOutput`. The mock's removal surface is dead code; either drop it or extend `cleanup()` to remove the output and assert `removedOutput`.

### Package and scheme wiring

`Package.swift` adds the `SharedScreens` library product, the target (depending on `DesignSystem`, processing `Styles/Media.xcassets` and `Styles/Strings`, with the SwiftLint plugin), and the `SharedScreensTests` test target — all correct, and `build-for-testing` plus the SwiftPM-generated scheme run the suite green. The committed Xcode scheme is the weak link. `Demo/DesignSystemDemo.xcodeproj/.../SharedScreensTests.xcscheme` lists `DesignSystemDemo.app` as the build/launch buildable and references the test bundle as `container:..` (the package), and in practice `xcodebuild ... -scheme SharedScreensTests` resolves to a "My Mac" destination and fails with "no test bundles available to test". As committed it cannot drive the tests; it should either target the SwiftPM test target directly or be removed in favour of the generated scheme.

### XIB forces an iOS build

`DialogView.xib` (`targetRuntime="iOS.CocoaTouch"`, `customModule="SharedScreens"`, `DialogBackground` named colour resolved from the bundled catalog) means the whole package fails to compile on macOS: `swift build` errors with `iOS xibs do not support target device type "mac"`. The iOS simulator build is clean, so this is a "must build for iOS" constraint rather than a defect, but it should be explicit in CI config and contributor docs so `swift build`/`swift test` aren't assumed to work locally.
